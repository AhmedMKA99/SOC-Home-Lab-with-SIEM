\section{Implementation}
\label{sec:implementation}

\subsection{Overview}

This section describes the specific technical implementation of the SOC home lab, at the level of concrete commands, configurations, and observed behaviour. It is deliberately more detailed than the Methodology section, and complements the Markdown build documents in the accompanying repository. Where relevant, the corresponding milestone from Section~\ref{sec:methodology} is noted.

\subsection{Host and Hypervisor (M1)}

The lab was built on a Windows 11 host machine equipped with an AMD Ryzen 5 8400F CPU (6 cores, 12 threads), 16~GB of RAM, and around 297~GB of free storage. Oracle VirtualBox version 7.2.8 was chosen as the hypervisor for its ubiquity, its native NAT Network feature, and its cross-platform compatibility.

Given the 16~GB RAM constraint, a deliberate operational policy was adopted: the Wazuh server and one endpoint are run at a time during heavy work, with the second endpoint powered off. Both endpoints can run simultaneously for lighter tasks. This is a genuine limitation but does not invalidate the design.

\subsection{Isolated Lab Network (M1)}

A dedicated VirtualBox NAT Network named \texttt{SOC-Lab} was created for the entire lab, on the subnet 10.0.10.0/24 with DHCP enabled and IPv6 disabled. Every virtual machine in the project was attached to this network and only this network. To allow the Wazuh dashboard to be reached from the host browser without exposing the lab to any real network, a single port-forwarding rule was defined:

\begin{quote}
\texttt{VBoxManage natnetwork modify --netname "SOC-Lab" \\
--port-forward-4 "wazuh-dashboard:tcp:[]:8443:[10.0.10.3]:443"}
\end{quote}

The result is that the dashboard is reachable at \texttt{https://localhost:8443} from the host, while the lab itself remains fully isolated. All three virtual machines received DHCP-assigned addresses in the 10.0.10.0/24 range:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Component} & \textbf{Address} \\
\midrule
NAT gateway & 10.0.10.1 \\
Wazuh server & 10.0.10.3 \\
Windows endpoint & 10.0.10.4 \\
Linux endpoint & 10.0.10.5 \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Wazuh Server Deployment (M2)}

The Wazuh server was deployed from the official Wazuh OVA appliance (version 4.14.5), which ships the manager, indexer, and dashboard pre-installed and pre-configured. Using the appliance in place of a manual install removed setup friction and allowed the project to focus on SOC work rather than on Wazuh installation.

Import settings adjusted for the 16~GB host:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Setting} & \textbf{Value} \\
\midrule
Base memory & 6144 MB \\
CPU & 2 vCPUs \\
Network adapter & NAT Network \texttt{SOC-Lab} \\
\bottomrule
\end{tabular}
\end{center}

On first boot, the appliance received the address 10.0.10.3 via DHCP. The dashboard was then accessible over HTTPS at \texttt{https://localhost:8443} via the port-forwarding rule, with the appliance's default credentials (username \texttt{admin}, password \texttt{admin}). These credentials are default lab values; a production deployment would rotate them immediately.

\subsection{Windows Endpoint (M3)}

The Windows endpoint was provisioned from Microsoft's freely provided \texttt{WinDev2407Eval.ova} appliance (Windows 11, 90 day evaluation), imported with 4096~MB of RAM and 2 vCPUs, and attached to the \texttt{SOC-Lab} network. The endpoint received DHCP address 10.0.10.4.

The Wazuh Windows agent was installed using the command generated by the dashboard's \textit{Deploy new agent} wizard, pointed at manager address 10.0.10.3 with agent name \texttt{Windows-Endpoint} in the \texttt{default} group. The service was then started (\texttt{NET START WazuhSvc}) and the agent appeared as Active on the dashboard.

Because the default Windows Event Log does not by itself provide adequate visibility for behavioural detection, \textbf{Sysmon} was installed with the widely-adopted SwiftOnSecurity baseline configuration. This provides detection-grade endpoint telemetry, including process creation, network connections, image loads, and file activity. Sysmon logs to the \texttt{Microsoft-Windows-Sysmon/Operational} event channel; the Wazuh agent was configured to read this channel by adding a \texttt{<localfile>} entry to \texttt{C:\textbackslash{}Program Files (x86)\textbackslash{}ossec-agent\textbackslash{}ossec.conf}, then restarting the agent.

\subsection{Linux Endpoint (M3--M4)}

The Linux endpoint was installed manually from the Ubuntu Desktop 26.04 LTS ISO onto a new VirtualBox VM (4096~MB RAM, 2 vCPUs, 30~GB disk, attached to \texttt{SOC-Lab}). The endpoint received DHCP address 10.0.10.5.

The Wazuh Linux agent was installed via the DEB package generated by the same dashboard wizard, and the service enabled and started with \texttt{systemctl}. The agent appeared as agent ID 002 on the dashboard.

To provide command-execution telemetry equivalent to Sysmon on Windows, the Linux Audit framework (\texttt{auditd}) was installed. Two audit rules were added to \texttt{/etc/audit/rules.d/wazuh.rules} tracking every \texttt{execve} system call (the syscall invoked whenever any command is executed), keyed with \texttt{audit-wazuh-c} for identification. The rules were loaded with \texttt{augenrules --load} and verified with \texttt{auditctl -l}. The Wazuh Linux agent by default reads \texttt{/var/log/audit/audit.log}, so no further agent configuration was required beyond restarting \texttt{wazuh-agent}.

At this point, both endpoints were delivering detection-grade telemetry to the SIEM: Sysmon on Windows for process, network, and file events; \texttt{auditd} on Linux for command execution. Milestone M4 was complete.

\subsection{Attack Simulations (M5)}

Four simulations were executed in the lab. Each is summarised below with the technique targeted, the commands issued, and the alerts observed.

\textbf{Simulation 1, Windows account creation and privilege escalation (T1136.001, T1078.003).} From an elevated PowerShell session on the Windows endpoint, the commands \texttt{net user testuser P@ssw0rd123! /add} and \texttt{net localgroup administrators testuser /add} were executed. Within 60 seconds, Wazuh produced a cluster of correlated alerts including ``Users Group Changed'' (Level 8), ``Administrative Privilege Assigned'' (Level 12), ``Domain Users Group Changed'' (Level 8), ``A \texttt{net user} account discovery command was executed'' (Level 3), and multiple Sysmon-based alerts for the underlying process creation. This is the incident written up in full as \textbf{INC-2026-001} in the accompanying \texttt{incident-reports/} folder.

\textbf{Simulation 2, Linux account creation and privilege escalation.} The commands \texttt{sudo useradd -m testuser}, a password set via \texttt{chpasswd}, and \texttt{sudo usermod -aG sudo testuser} were executed on the Linux endpoint. Wazuh produced ``New group added to the system'' (Rule 5901, Level 8), ``New user added to the system'' (Rule 5902, Level 8), ``Successful sudo to ROOT executed'' (Rule 5402, Level 3), and PAM session-lifecycle alerts. This validated end-to-end delivery of \texttt{auditd} telemetry into Wazuh.

\textbf{Simulation 3, failed sudo attempts (T1110).} The user's sudo credential cache was invalidated with \texttt{sudo -k}, then a sudo command was executed with four consecutive wrong passwords. Wazuh produced ``\texttt{unix\_chkpwd}: Password check failed'' (Rule 5557, Level 5) for each attempt, plus ``PAM: User login failed'' (Rule 5503, Level 5). Under sufficient failure velocity, Wazuh's correlation rules would additionally produce ``Multiple authentication failures'' at a higher level; this was not observed within the small number of attempts used.

\textbf{Simulation 4, Windows hosts file modification (FIM test).} A benign entry was appended to \texttt{C:\textbackslash{}Windows\textbackslash{}System32\textbackslash{}drivers\textbackslash{}etc\textbackslash{}hosts} using PowerShell's \texttt{Add-Content}. No real-time FIM alert appeared in Wazuh within the observation window. This is a genuine and useful finding, not a failure: Wazuh's default FIM configuration runs on a scheduled basis (every 12 hours by default) rather than real-time, and the \texttt{hosts} file path is not specifically configured for real-time watching. This finding is captured as a recommendation in the incident report and in Section~\ref{sec:discussion}.

\subsection{Analyst Triage and Incident Reporting (M6)}

Simulation 1 was written up in full as an incident report (\texttt{INC-2026-001\_Windows\_Account\_Creation.docx}) following a standard analyst format: executive summary, incident details, timeline, detection and alerting, technical analysis, impact assessment (CIA triad), response actions (immediate, short-term, follow-up), root cause and findings, recommendations, and lessons learned, with MITRE ATT\&CK mappings throughout. A reusable blank template of the same format is included in the repository for future incidents.
