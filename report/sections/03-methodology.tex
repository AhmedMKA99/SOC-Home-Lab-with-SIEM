\section{Methodology}
\label{sec:methodology}

\subsection{Overall Approach}

The project followed an iterative \textbf{build $\rightarrow$ verify $\rightarrow$
document} cycle. Each component of the lab was deployed in isolation, its
correct operation was confirmed with a small controlled test before the next
component was added, and the steps used were recorded at the time they were
performed rather than reconstructed after the fact. This approach was chosen
for three reasons. First, the fastest way to discover a broken assumption in a
security build is to test the smallest possible piece before extending it.
Second, documentation written contemporaneously is meaningfully more accurate
than documentation written after the fact, particularly for the exact commands
and configuration values that determine whether a deployment will reproduce.
Third, the reproducibility of the lab was itself a project deliverable, so the
documentation was treated as a first-class artefact throughout, not as a
retrospective write-up.

\subsection{Environment Design}
\label{sec:env-design}

The lab was designed around three constraints and one non-negotiable safety
requirement. The constraints were: a single physical host with 16 GB of RAM,
one hypervisor (Oracle VirtualBox), and the requirement that all components
should be reproducible on any consumer-grade Windows machine. The safety
requirement was that the environment must be fully isolated from any
production network: no traffic from the lab could reach the wider Internet or
the host network without deliberate configuration.

Isolation was achieved by placing all virtual machines on a VirtualBox
\textit{NAT network} named \texttt{SOC-Lab} on the address range
\texttt{10.0.10.0/24}. This is distinct from VirtualBox's default NAT
mode: a NAT network permits VM-to-VM communication on the same segment while
still translating outbound traffic through the host, which was necessary for
initial package downloads but was subsequently locked down. The address plan
allocated one address per role: \texttt{10.0.10.3} for the SIEM manager,
\texttt{10.0.10.4} for the Windows endpoint, and \texttt{10.0.10.5} for the
Linux endpoint. Keeping the address assignments deterministic simplified both
the Wazuh agent enrolment and the later analysis, since the source of every
log line could be identified from its IP alone.

The 16 GB host RAM constraint meant that not all VMs could run
simultaneously under load. In practice, the Wazuh manager was always
running (its role required continuous operation to receive telemetry), and
the two endpoints were run in alternation for heavy testing.

\label{sec:tools}

be free or open-source, it had to be genuinely used in industry, and its
core concepts had to transfer to commercial equivalents rather than being

The most significant of these choices is \textbf{Wazuh}, which was preferred
over Splunk Free (data cap and no long-term retention), Elastic Security
(more complex initial deployment for a single learner), and Security Onion
(more focused on network detection than endpoint monitoring in the shape
required for this project). Wazuh's out-of-the-box combination of manager,
indexer, dashboard, and agent, with a pre-populated ruleset that already
recognises common attack patterns, offered the best balance of depth and
setup effort for a single-analyst home lab.

\subsection{Endpoint Telemetry Strategy}
\label{sec:telemetry-strategy}

A recurring theme in the literature review was that default operating-system
logs are insufficient for meaningful behavioural detection. The methodology
therefore treated \textit{deliberate endpoint telemetry enhancement} as a
mandatory step, not an optional one. Both endpoints were provisioned with
their platform's equivalent of detection-grade logging.

On \textbf{Windows}, this meant installing Sysmon with the SwiftOnSecurity
baseline configuration and then extending the Wazuh agent configuration to
forward the \texttt{Microsoft-Windows-Sysmon/Operational} event channel to the
manager. Without this addition, the Wazuh agent would have received only
the standard Windows Security Event Log; with it, the agent received the
process-creation, network-connection, and file-modification records that
modern detection depends on.

On \textbf{Linux}, the equivalent step was installing the \texttt{auditd}
daemon and adding audit rules for the \texttt{execve} system call, tagged with
the \texttt{audit-wazuh-c} key so command-execution events could be
distinguished from other audit traffic. Wazuh's default Linux agent
configuration already parses \texttt{/var/log/audit/audit.log} once auditd is
present, so no further Wazuh-side configuration was required.

This paired approach --- Sysmon on Windows, auditd on Linux --- reflects real
SOC practice, where both platforms need their own deliberate telemetry
enhancement to produce comparable visibility.

\subsection{Attack Simulation Design}
\label{sec:sim-design}

Attack simulations were designed against three principles.

\textbf{First, safety.} All simulations used benign emulated behaviour rather
than live malware or real exploitation. Where a technique required the
creation of an artefact (a user, a group, a file entry), the artefact was
reversible; where it required a command, the command was benign in isolation
and only meaningful in aggregate. This is consistent with community
guidance on running attack simulations in home labs and with the intent of
tooling such as Atomic Red Team~\cite{atomicredteam}.

\textbf{Second, coverage across the two platforms.} The simulations were
distributed across Windows and Linux endpoints, and across multiple ATT\&CK
tactic categories (specifically Persistence, Privilege Escalation, Credential
Access, and Defence Evasion), rather than concentrated on a single technique
family. This ensured that the resulting evaluation could speak to lab
coverage as a whole, not merely to how well one technique was detected.

\textbf{Third, at least one intentionally negative test.} One simulation was
designed with the expectation that the default Wazuh configuration would
\textit{not} detect the activity, because a lab that only ever produces
successful detections is not being honestly stress-tested. A negative result,
when it identifies a specific configuration gap that can be closed, is as
valuable as a positive result. This is discussed further in the Evaluation
(Section~\ref{sec:evaluation}) and Discussion (Section~\ref{sec:discussion}).

\subsection{Triage and Documentation Approach}
\label{sec:triage-approach}

Each simulation was followed by a structured triage exercise mimicking the
work of a Tier~1 SOC analyst. The steps applied to every simulation were:

\begin{enumerate}[label=\textbf{T\arabic*.},leftmargin=*]
    \item Observe the Wazuh dashboard within a defined window (typically one
          minute) after the simulated activity was performed.
    \item Identify the alerts produced, capturing rule ID, rule description,
          and severity level for each.
    \item Classify each alert as a true positive (correctly identified
          malicious-shaped activity), a false positive (a benign event
          erroneously flagged), or expected background noise.
    \item Map the observed activity to the corresponding MITRE ATT\&CK
          technique(s) where applicable.
    \item Capture a screenshot of the dashboard state as evidence.
    \item Write a full analyst-style incident report for the simulation,
          treating the events as if they were unplanned.
\end{enumerate}

Producing an incident report for every simulation --- rather than only
recording the raw alerts --- was a deliberate methodological choice. It forces
a level of structured reasoning about impact, response, and remediation that
is not required when merely observing that an alert appeared. The incident
report artefacts are stored in the project's \texttt{incident-reports/}
directory and are considered part of the deliverable set.
