\section{Evaluation}
\label{sec:evaluation}

\subsection{Overview}

This section evaluates the completed lab against the objectives set out in
Section~\ref{sec:aim} and the success criteria in the Initial Project
Overview. Four attack simulations were executed across the two endpoints,
and each was subject to the structured triage process described in
Section~\ref{sec:triage-approach}. For every simulation, the executed
activity, the alerts produced, the analyst classification, and the mapped
MITRE ATT\&CK technique(s) are documented. Full-length analyst-style
incident reports for each simulation are held in the project's
\texttt{incident-reports/} directory as \texttt{INC-2026-001} through
\texttt{INC-2026-004}. Screenshots referenced below are stored in the
\texttt{screenshots/} directory and form the evidence base for the
evaluation.

\subsection{Simulation 1 --- Windows Local Account Creation and Privilege Escalation}
\label{sec:sim1}

\textbf{Activity performed.} From an elevated PowerShell session on the
Windows endpoint, a new local account \texttt{testuser} was created and
immediately added to the local Administrators group:

\begin{quote}\small
\texttt{net user testuser P@ssw0rd123! /add}\\
\texttt{net localgroup administrators testuser /add}
\end{quote}

\textbf{ATT\&CK mapping.} T1136.001 (Create Account: Local Account) and
T1078.003 (Valid Accounts: Local Accounts).

\textbf{Detection result.} Within sixty seconds, the Wazuh dashboard
produced a cluster of correlated alerts. The most operationally significant
were \textit{Administrative Privilege Assigned} (Level~12), \textit{Users
Group Changed} (Level~8), and \textit{Discovery activity spawned by
PowerShell execution} (Sysmon-based, Level~5). The full alert cluster,
including several lower-level supporting events, is documented in
\texttt{INC-2026-001}.

\textbf{Classification.} True positive across all alerts. The correlation
across Sysmon process telemetry (net.exe spawned by powershell.exe) and
Windows Security event log entries (4720 for account creation, 4732 for
privileged group addition) provided independent confirmation of the same
underlying activity from two different data sources.

\subsection{Simulation 2 --- Linux Local Account Creation with Sudo Privilege}
\label{sec:sim2}

\textbf{Activity performed.} From a terminal session on the Linux endpoint,
a new local user was created, given a password, and added to the sudo group:

\begin{quote}\small
\texttt{sudo useradd -m testuser}\\
\texttt{echo "testuser:P@ssw0rd123!" | sudo chpasswd}\\
\texttt{sudo usermod -aG sudo testuser}
\end{quote}

\textbf{ATT\&CK mapping.} T1136.001 (Create Account: Local Account),
T1548.003 (Abuse Elevation Control Mechanism: Sudo and Sudo Caching), and
T1078.003 (Valid Accounts: Local Accounts).

\textbf{Detection result.} Within sixty seconds, alerts fired for
\textit{New user added to the system} (Rule 5902, Level~8), \textit{New
group added to the system} (Rule 5901, Level~8), and \textit{Successful
sudo to ROOT executed} (Rule 5402, Level~3), along with the corresponding
PAM session events. Full details are recorded in \texttt{INC-2026-002}.

\textbf{Classification.} True positive across all alerts. The detection
pattern is the direct Linux counterpart to Simulation~1, and the analyst
triage flow was near-identical, which suggests a single unified runbook
covering both platforms would be a natural detection engineering follow-up.

\subsection{Simulation 3 --- Repeated Failed Authentication on Linux Endpoint}
\label{sec:sim3}

\textbf{Activity performed.} Repeated incorrect passwords were entered at a
sudo prompt for a valid local account, mimicking the pattern of a
password-guessing attempt.

\textbf{ATT\&CK mapping.} T1110.001 (Brute Force: Password Guessing).

\textbf{Detection result.} Each failed attempt produced a paired alert
under Rule 5557 (\textit{unix\_chkpwd: Password check failed}, Level~5) and
Rule 5503 (\textit{PAM: User login failed}, Level~5). No higher-severity
aggregate alert was raised by the default ruleset, even though the
individual failures accumulated visibly on the dashboard. Full details are
recorded in \texttt{INC-2026-003}.

\textbf{Classification.} True positive individually; however, the absence
of a correlation rule that promotes a cluster of failed attempts into a
higher-severity aggregate alert is a documented detection engineering gap.
In a production environment, a Tier~1 analyst would rely on a dashboard
spike or a custom aggregate rule rather than paging on each individual
Level~5 event.

\subsection{Simulation 4 --- Negative Test, File Integrity Monitoring on Windows}
\label{sec:sim4}

\textbf{Activity performed.} A line was appended to the Windows hosts file
using PowerShell:

\begin{quote}\small
\texttt{Add-Content -Path "C:\textbackslash Windows\textbackslash System32\textbackslash drivers\textbackslash etc\textbackslash hosts" -Value "127.0.0.1 test-fim.local"}
\end{quote}

\textbf{ATT\&CK mapping.} T1565.001 (Stored Data Manipulation), with
adjacent relevance to T1556 (Modify Authentication Process) and to hosts
file abuse used in DNS-redirection attacks.

\textbf{Detection result.} \textbf{No File Integrity Monitoring alert
was produced within the observation window.} Other unrelated telemetry
(service startup type changes, executable creation events) continued to
appear on the dashboard, confirming the agent was still forwarding events
normally.

\textbf{Classification.} \textit{Negative result}, documented as a
detection gap in \texttt{INC-2026-004}. The root cause is the default
Wazuh syscheck configuration on Windows, which runs periodic scans (default
interval: 12 hours) rather than real-time file-change monitoring. Real-time
monitoring for a specific path requires adding
\texttt{realtime="yes"} to the corresponding
\texttt{<directories>} entry in the agent configuration. The incident
report proposes the specific configuration change that would close this
gap, together with a wider recommendation to enable real-time FIM
selectively on a defined set of security-critical files across both
platforms.

\subsection{Evaluation Against Success Criteria}

The Initial Project Overview defined success in four specific terms. Each is
addressed below.

\textbf{Criterion 1: The SIEM is operational with two or more endpoints
actively reporting.} \textit{Met.} The Wazuh manager, indexer, and dashboard
were deployed and remained operational throughout the evaluation period,
with two enrolled endpoints (Windows and Linux) both appearing as
\texttt{Active} in the dashboard and both forwarding both default and
enhanced telemetry.

\textbf{Criterion 2: At least four distinct security events have been
simulated and detected.} \textit{Met.} Four distinct simulations were
executed as described in this section, three producing true-positive alerts
and the fourth producing a documented negative result (which is itself a
valid detection engineering finding, not a failure).

\textbf{Criterion 3: Each detection is documented with triage notes and a
true/false-positive classification.} \textit{Met.} Every simulation has a
corresponding full analyst-style incident report
(\texttt{INC-2026-001} through \texttt{INC-2026-004}) with executive
summary, timeline, detection detail, technical analysis, impact assessment,
response actions, and recommendations. Each alert has been classified.

\textbf{Criterion 4: A third party can reproduce the lab by following the
published guide.} \textit{Met, subject to the usual caveats of hypervisor
and OS version drift.} The build documentation (\texttt{docs/01} through
\texttt{docs/04}) is written as a step-by-step reproducible guide, records
exact versions of the software used, and is published to the project's
public GitHub repository alongside this report and the incident reports.

\subsection{Evaluation Against Project Objectives}

The seven objectives from Section~\ref{sec:aim} were met as follows: O1
(deploy an open-source SIEM), O2 (configure two monitored endpoints), and
O3 (enable enhanced host telemetry) are demonstrated in
Section~\ref{sec:implementation}. O4 (verify centralised log collection and
baseline normal activity) was completed prior to running any simulation, as
described in Section~\ref{sec:impl-verify}. O5 (simulate security events)
and O6 (triage the alerts and classify them) are covered by the four
simulations documented above. O7 (produce a fully reproducible record of
the build) is met by the combination of this report, the \texttt{docs/}
build documents, and the accompanying GitHub repository.
