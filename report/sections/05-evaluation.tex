\section{Evaluation}
\label{sec:evaluation}

\subsection{Overview}

This section evaluates the completed lab against the objectives set out in Section~\ref{sec:aim}, using the evidence gathered during the build and simulation phases. It also considers what the observed behaviour tells us about the wider question of how closely a home lab can represent professional SOC operations.

\subsection{Evaluation Against Objectives}

Each objective from Section~\ref{sec:aim} is addressed in turn.

\textbf{O1: Deploy an open-source SIEM server on an isolated virtual network.} Met. The Wazuh 4.14.5 appliance was deployed to a dedicated VirtualBox NAT Network (\texttt{SOC-Lab}, 10.0.10.0/24), and the dashboard was made reachable from the host through a single explicit port-forwarding rule while the wider lab remained isolated. The dashboard, indexer, and manager were all functioning correctly on first boot.

\textbf{O2: Configure two monitored endpoints, one Windows and one Linux, each reporting to the SIEM.} Met. Both endpoints were successfully enrolled and consistently visible as \texttt{Active} on the dashboard. The Windows endpoint was assigned agent name \texttt{Windows-Endpoint}; the Linux endpoint became agent ID 002.

\textbf{O3: Enable enhanced host telemetry beyond default operating-system logs.} Met. On Windows, Sysmon was installed with the SwiftOnSecurity baseline and its event channel was integrated into the Wazuh agent configuration. On Linux, \texttt{auditd} was installed and configured with \texttt{execve} rules keyed for identification. Both feeds were confirmed to be flowing into the SIEM.

\textbf{O4: Verify centralised log collection and establish a baseline of normal activity.} Met. The Wazuh dashboard consistently displayed events from both endpoints in a single unified view, and background system activity was observable as expected baseline noise before any simulations began.

\textbf{O5: Simulate a set of security events and observe the resulting alerts.} Met. Four simulations were executed spanning multiple detection classes (account management, privilege escalation, failed authentication, file integrity). Three of the four produced clearly visible, correlated alerts within 60 seconds of the triggering action. The fourth (FIM) did not produce a real-time alert, which is itself a valid and useful finding, discussed in Section~\ref{sec:discussion}.

\textbf{O6: Triage the alerts, classifying them and documenting the reasoning.} Met. All four simulations were reviewed via the Wazuh Threat Hunting view, screenshots captured, and the most operationally significant simulation (Simulation 1) was written up as a full incident report following a standard analyst format.

\textbf{O7: Produce a fully reproducible record of the build so the lab can be rebuilt by a third party.} Met. The repository contains four Markdown build documents (\texttt{docs/01} through \texttt{docs/04}) covering each stage of the build in step-by-step form, a formal LaTeX report (this document), incident report artefacts, and screenshots. The full project is public at \texttt{github.com/AhmedMKA99/SOC-Home-Lab-with-SIEM}.

\subsection{Quantitative Observations}

Although the lab is not sized to produce meaningful performance metrics, some observations are worth recording.

\textbf{Detection latency.} For every simulation that produced an alert, the time between the triggering action and the corresponding alert appearing in the dashboard was well under 60 seconds. This meets the informal expectations for time-to-detect at the Tier 1 SOC level for host-based activity of the kind simulated.

\textbf{Alert volume.} Simulation 1 alone produced approximately 20 correlated alerts across multiple rule families, out of a broader 24-hour count of 463 events for the Windows endpoint. This is realistic in shape: a genuine attacker action produces not one alert but a cluster of related alerts, and separating signal from noise is a core analyst skill.

\textbf{Severity distribution.} Across the alerts generated by Simulation 1, rule levels ranged from 3 (informational) to 12 (high priority, would page an on-call analyst in a live SOC). Simulation 2 produced alerts at Levels 3 and 8. Simulation 3 produced only Level 5 alerts because the small number of failed attempts did not cross the correlation threshold for a higher-priority ``multiple failures'' alert.

\subsection{Detection Coverage}

Coverage is not comprehensive, but it is representative. The four simulations exercised four different Wazuh capability classes:

\begin{itemize}[leftmargin=*]
    \item Windows Security Event Log correlation (Simulation 1)
    \item Sysmon-based behavioural detection (Simulation 1)
    \item Linux \texttt{auditd} command telemetry (Simulations 2 and 3)
    \item Linux PAM authentication events (Simulation 3)
    \item Windows File Integrity Monitoring (Simulation 4, with an important finding on default configuration)
\end{itemize}

For a graduate-level demonstration project, this breadth is sufficient to prove that the lab exercises the SIEM across multiple detection paradigms, not just one.

\subsection{Reproducibility Check}

The repository has been reviewed for the presence of every artefact required to rebuild the lab from a clean state: the four build documents, the isolated network specification, the appliance and ISO references (with instructions on where to download them, since they are too large to redistribute), the specific configuration snippets used, and the exact commands issued for each simulation. Screenshots of expected outcomes are present for comparison. A third party with a comparable host machine and a few hours of time could rebuild the lab from these artefacts alone.

\subsection{Limitations Observed}

Two limitations became apparent during evaluation and are worth naming honestly.

\textbf{Wazuh FIM is not real-time by default.} As shown in Simulation 4, modifying a monitored file did not trigger a real-time alert with default settings. This is a configuration limitation, not a bug: real-time FIM must be explicitly enabled per-path. A production deployment would enable it on high-value paths as standard, and a follow-on version of this lab would do the same.

\textbf{Correlation rules need volume to fire.} The ``multiple authentication failures'' correlation rule in Simulation 3 did not fire because only four attempts were made in the observation window. A more aggressive simulation would trigger it. This is a useful reminder that correlation-based detection depends on activity crossing thresholds, and that isolated events at low severity can look benign until they are aggregated.

Neither of these limitations invalidates the lab. They are, if anything, evidence that the lab is doing what it should: producing observations that would prompt genuine tuning decisions in a real environment.
